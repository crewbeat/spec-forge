# Forge

Програмна фабрика для Claude Code, у якій ви самі вирішуєте, де працює агент, а де потрібне ваше слово.

Задача проходить конвеєр: intake оцінює її та пропонує, скільки процесу їй потрібно; за потреби пишеться специфікація, проєктується рішення й окремий агент наперед пише тести; будівник робить зміну в окремому worktree; скрипт запускає перевірки вашого репозиторію; рев'юери з чистим контекстом читають diff; далі коміт, пуш, PR і злиття — кожен крок за вашим налаштуванням.

Що перевірено, а що ще ні, чесно описано в розділі [Стан](#стан).

## Встановлення

```bash
./install.sh /шлях/до/вашого/репозиторію
```

Потрібні git, `python3` 3.9+ (без додаткових пакетів) і Claude Code. Для PR і задач із GitHub потрібен `gh`, у якому ви вже ввійшли.

Той самий скрипт оновлює вже встановлену фабрику: ваші `forge/config.json` і `forge/checks.sh` він не чіпає, а ключі, яких у старому конфігу немає, отримують значення за замовчуванням.

Після встановлення:

1. Впишіть у `forge/checks.sh` команди тестів, лінту й збірки. Поки файл не заповнено, жодна зміна не пройде перевірку.
2. Перегляньте `forge/config.json`.
3. Закомітьте нові файли. Worktree задачі створюється з гілки `base_branch`, тому фабрика має бути в ній.

## Користування

У Claude Code в корені репозиторію:

```
/forge run             запустити або продовжити всі задачі
/forge new <задача>    додати задачу й запустити
/forge dashboard       відкрити дашборд
/forge <будь-що>       питання про задачу, відповідь, схвалення, правки
```

Задачі надходять чотирма шляхами: командою `/forge new`, кнопкою **New task** на дашборді, `.md`-файлом у теці `forge/inbox/` (перший заголовок `#` стає назвою) або з [GitHub Issues](#задачі-з-github-issues).

Стан кожної задачі лежить у `forge/jobs/<id>/`. Якщо сесію закрито, `/forge run` у новій сесії продовжить кожну задачу з її стадії.

## Де бере участь людина

Блок `human` у `forge/config.json`:

| Ключ | Значення | Що означає |
|---|---|---|
| `intake` | `approve` \| `auto` | Підтверджувати рішення intake й профіль, чи довіритися йому |
| `questions` | `ask` \| `assume` | Агент ставить питання, коли без вас не обійтися, чи робить припущення й записує їх |
| `plan` | `approve` \| `auto` | Затверджувати специфікацію перед початком роботи |
| `design` | `approve` \| `auto` | Затверджувати архітектуру, рішення й контракти (профілі зі стадією `design`) |
| `dependencies` | `approve` \| `auto` | Дозволяти нові залежності, які додає зміна |
| `ui_check` | `approve` \| `off` | Самому подивитися на UI перед доставкою (лише задачі з інтерфейсом) |
| `commit` | `auto` \| `approve` \| `off` | Коміт у гілку задачі |
| `push` | `auto` \| `approve` \| `off` | Пуш гілки |
| `pull_request` | `auto` \| `approve` \| `off` | Створення PR |
| `merge` | `auto` \| `approve` \| `off` | Злиття PR |

Кроки доставки йдуть по порядку. `off` зупиняє задачу перед цим кроком: наприклад, `"commit": "off"` залишає зміни в worktree незакоміченими. За замовчуванням коміт автоматичний, пуш і PR чекають на схвалення, злиття вимкнене.

Ключ `delivery` визначає, куди йде зміна: `github` (пуш, PR, злиття через `gh`), `local` (коміт і злиття гілки задачі в `base_branch` прямо в основній копії, без віддаленого репозиторію) або `auto` — `github`, якщо є `origin`, інакше `local`. Локальне злиття підкоряється тому самому `human.merge` і відмовляється працювати, якщо основна копія не на `base_branch` або має незакомічені зміни.

Відповісти можна в чаті Claude Code або на дашборді. Питання агентів обговорюються в чаті.

## Профілі

Профіль визначає, скільки процесу отримує задача. Intake пропонує його, ви підтверджуєте або змінюєте.

| Профіль | Стадії | Для чого |
|---|---|---|
| `quick` | build → review | Дрібні правки, конфіги |
| `medium` | spec → build → review | Звичайні фічі |
| `full` | spec → design → tests → build → review, більше схвалень, сильніша модель рев'ю | Гроші, авторизація, публічний API, міграції |

Профіль може перевизначити і блок `human`, і моделі. Список стадій, схвалення та моделі кожного профілю задаються в `profiles`; стадії `spec`, `design`, `tests` і `review` можна вмикати в будь-якому профілі, порядок завжди той самий.

### Стадії design і tests

- **design.** Архітектор пише `design.md`: архітектуру, рішення з альтернативами й ціною (як ADR), точні контракти та впорядкований список малих задач для будівника. Це робочий документ задачі; після злиття джерелом правди лишається код.
- **tests.** Тестувальник пише тести до початку збірки, зі специфікації та контрактів. Скрипт запам'ятовує хеш кожного файлу, який той додав чи змінив, і перевірка провалюється, якщо будівник такий файл зачепив. Якщо тест справді хибний, будівник повертає `DISPUTE`, тестувальник розглядає зауваження, і збірка йде далі; кожна суперечка рахується як раунд.

## Моделі

Блок `models` задає модель для кожної ролі: `intake`, `spec-writer`, `architect`, `tester`, `builder`, `reviewer-code`, `reviewer-ui`. Значення: `haiku`, `sonnet`, `opus`, `fable`. Блок `risk_models` підміняє моделі для задач, які intake оцінив як ризиковані.

## Що вирішує скрипт, а не агент

- **Перехід між стадіями.** `forge/bin/forge` єдиний змінює стан задачі й каже оркестратору, що робити далі.
- **Перевірки.** `forge/checks.sh` запускається з основної копії репозиторію, тому задача не може змінити перевірки, якими її оцінюють. Невдала збірка не доходить до рев'юера.
- **Захищені шляхи.** Зміна файлів із `protected_paths` провалює перевірку.
- **Тести тестувальника.** Після стадії `tests` їх не може змінити ніхто, крім самого тестувальника.
- **Нові залежності.** Див. нижче.
- **Git.** Агенти не комітять і не пушать; це робить скрипт, і лише так, як дозволяє `human`.
- **Ліміт раундів.** Після `max_rounds` невдалих спроб задача чекає на ваші вказівки.

## Нові залежності

Агент може назвати пакет, якого не існує, або такий, що з'явився тиждень тому під вгаданою назвою. Тому перевірка порівнює маніфести зміни з базовим комітом (`package.json`, `composer.json`, `requirements*.txt`, `go.mod`, `Gemfile`) і для кожного нового пакета питає публічний реєстр, чи він існує і коли вперше опублікований.

- Пакета немає в реєстрі: перевірка провалена, будівник отримує це у звіті.
- Пакет молодший за `min_age_days` (30): задача чекає на вас, навіть якщо `human.dependencies` — `auto`.
- Інакше діє `human.dependencies`: `approve` питає один раз на пакет, `auto` лише записує список у `checks.md`.

Для `pyproject.toml`, `Cargo.toml`, `pom.xml` і Gradle фабрика бачить лише, що файл змінено, і показує це без назв пакетів. Блок `dependencies` у конфігу: `registry_check: false` вимикає запити до реєстрів (назви нових пакетів тоді нікуди не надсилаються), `ignore` — шаблони назв приватних пакетів, яких у публічному реєстрі немає, наприклад `"@acme/*"`.

## Задачі з GitHub Issues

```json
"github": { "enabled": true, "label": "forge", "repo": "", "poll_seconds": 120, "comment": false }
```

Відкриті issue з міткою `label` стають задачами; кожне береться один раз. `repo` порожній — це репозиторій, у якому стоїть фабрика, інакше `owner/name`. GitHub опитується на старті `/forge run`, а далі не частіше ніж раз на `poll_seconds`. З `"comment": true` фабрика пише в issue, коли взяла задачу і чим вона закінчилась; PR такої задачі містить `Closes #N`.

Мітка тут є перепусткою: у публічному репозиторії issue може відкрити будь-хто, а мітку ставить лише той, хто має права. Текст issue, як і будь-якої задачі, потрапляє до агентів лише як дані в `task.md`.

## Задачі, що залежать одна від одної

Задача може назвати ті, на яких вона будується, рядком на початку тексту:

```
# Ігровий екран

After: 6-game-session.md

...
```

Після `After:` ідуть номер задачі (`6`), її id або ім'я файлу з inbox, якщо задачі кинуто разом; кілька розділяються комами. Кузня не починає таку задачу, доки всі названі не завершені (злиті або відхилені), тож її робоча копія вже містить їхній код. На дашборді й у `forge status` видно «Waits for 006».

```bash
forge/bin/forge new "Екран" --after 6       # нова задача, що чекає на 006
forge/bin/forge after 8 7                    # змінити, на що чекає ще не почата задача
forge/bin/forge after 8                      # не чекати ні на що
```

Якщо в робочій копії задачі ще ніхто нічого не писав, а базова гілка пішла вперед, кузня перед запуском агента сама пересуває копію на свіжу базу.

## Вартість

Оркестратор передає скрипту кількість токенів кожного агента, якщо Claude Code її повідомив; `forge status` і дашборд показують суму на задачу і час роботи агентів. Доларів за замовчуванням немає: впишіть у `prices` свою ціну за мільйон токенів для кожної моделі (`{"sonnet": 6, "opus": 30}` — приклад формату, не справжні ціни), і з'явиться оцінка. Вона груба, бо вхідні, вихідні й кешовані токени рахуються за однією ціною.

## Дашборд

```bash
forge/bin/forge serve
```

Показує задачі за стадіями, окремо ті, що чекають на вас, файли кожного кроку, час у роботі, час очікування й токени. Звідти можна схвалити, повернути з коментарем, відхилити й додати задачу. Сервер слухає лише `127.0.0.1` і сам агентів не запускає: рішення підхоплює сесія Claude Code, де працює фабрика.

## Прибирання й облік

```bash
forge/bin/forge status           # один рядок на задачу
forge/bin/forge usage            # токени кожного запуску агента
forge/bin/forge clean            # прибрати worktree завершених задач
forge/bin/forge clean --force    # те саме, навіть якщо в worktree є незакомічені зміни
```

`clean` чіпає лише злиті й відхилені задачі; гілка задачі лишається.

## Нове джерело задач

Джерела живуть у `forge/lib/forgelib/sources.py`; GitHub Issues там займає близько 60 рядків і годиться за зразок. Щоб додати трекер, напишіть функцію, що створює задачі з `{source, ref, title, body, url}`, і за бажанням функцію, що повідомляє джерелу про результат; зареєструйте їх і ввімкніть у `sources` конфігу. Конвеєр про джерело нічого не знає.

## Тести

```bash
python3 -m unittest discover -s tests
```

Тести копіюють `forge/` у тимчасовий git-репозиторій і проганяють справжній CLI, граючи роль агентів.

## Стан

Перевірено тестами (18 наскрізних, зі справжнім git і підставним `gh`): ядро стану, конвеєр, усі точки схвалення, ліміт раундів, захищені шляхи, стадії design і tests із блокуванням тестів і суперечкою, пауза на нових залежностях, джерела «тека», «вручну» і GitHub Issues, коміт, пуш у справжній bare-репозиторій, локальне злиття, облік токенів, сервер дашборда. Запити до реєстрів npm, PyPI, Packagist, RubyGems і Go перевірено вручну на справжніх і вигаданих пакетах.

Перевірено на практиці: на окремому проєкті фабрика зі справжніми агентами через `/forge run` довела до злиття вісім задач поспіль — одну з профілем `quick` і сім із `medium`, від одного до чотирьох раундів кожна. Працювали intake, специфікація, будівник, рев'юери коду й UI, питання агентів до людини, схвалення на дашборді й у чаті, локальна доставка (коміт і злиття без віддаленого репозиторію) та облік токенів із транскриптів Claude Code.

Написано, але ще не перевірено на практиці:

- профіль `full` зі справжніми агентами: стадії `design` і `tests`, промпти архітектора й тестувальника;
- справжній `gh`: список issue, коментарі, пуш, створення й злиття PR (у тестах його грає скрипт-заглушка);
- пауза на нових залежностях у живому прогоні.

Ще не зроблено:

- інші трекери (Jira, Linear, GitLab);
- назви нових пакетів із `pyproject.toml`, `Cargo.toml`, Maven і Gradle;
- автоматична перевірка, що тести тестувальника спершу падають;
- рев'ю моделлю іншого вендора;
- спостереження після деплою.
